# 记录规程

记一条变动时照这份做。人和 Claude 都按同一套。

## 先判断：这件事该不该记

只有满足下面任意一条才记：

1. 改变了某个**数字**（指引、积压订单、capex、估值、利率定价、CDS……）；
2. 改变了某段**关系**（新订单、新投资、新担保、条款变更）；
3. 是一个**验证点的结果**（之前记过"到那天看什么"，现在结果出来了）。

评论、预测、情绪、"某分析师认为"——不记。同一件事被多家转载——只记一次，信源写最初发布的那一家。

## 一条变动的字段（`data/ledger/changes.json`）

| 字段 | 写法 |
| --- | --- |
| `id` | `ch-<主体>-<关键词>-<MMDD>` |
| `date` / `session` | 事件发生的美东日期；`pre` 盘前、`intra` 盘中、`post` 盘后。这决定市场反应从哪根 K 线算起，拿不准就查发布时间。 |
| `entity` | 主体 id。提到谁就记在谁名下。 |
| `related` | 直接受影响的其他主体，**最多 2 个**。 |
| `metric` | 如果改的是 `metrics.json` 里的某个数字，写它的 id，并同时给那个指标的 `history` 追加一条。 |
| `title` | 一句话，只说发生了什么。不用"利好 / 利空 / 重磅 / 暴跌"这类词。 |
| `from` / `to` | 之前是什么，现在是什么。没有"之前"就只写 `to`。 |
| `detail` | 两三句补充事实。 |
| `src` | `sources.json` 里的 id。没有就先加一条。 |
| `novelty` | `new` 首次出现；`expected` 与此前指引或一致预期相符；`repeat` 已披露信息的重复。`noveltyNote` 写依据（"此前指引是多少""一致预期是多少"）。 |
| `verify` | 指向 `calendar.json` 的一个验证点。没有合适的就新建一个：日期 + 到时候看什么。 |
| `caveat` | 口径不一致、来源互相矛盾、数字未经核实时，在这里写明。 |
| `noReaction` | 不该算市场反应时写原因（如"日期未核实"）。 |

## 信源（`data/ledger/sources.json`）

- `pub` 写**最初的发布方**；如果是经别人转述才看到的，把转述方写在 `via`。
- `type` 只描述类别，不评价真假：
  `filing` 一手披露（公告、招股书、官方讲稿）· `media` 媒体报道 · `anon` 匿名消息（"知情人士"）· `research` 机构研究 · `data` 行情数据 · `aggregate` 二手汇总 · `personal` 个人账号。

## 不做的事

- 不写结论，不写"看多 / 看空"，不给信源打可信度分。
- 不手填市场反应——它由服务端按行情算出来。
- 不把"待整理"里的标题直接当变动：先找到原始出处，再按上面的字段整理。

## 记完之后

```bash
npm run check
```

通过之后刷新页面即可（服务端每次请求都重新读数据）。新增上市标的时：给主体写上 `ticker`（今年才上市的再写 `listed`），接通实时后服务会自动拉它最近一年的日线；没接实时就先用 `npm run import` 导入，否则市场反应会显示"待收盘"。IPO 还没开始交易的主体写 `ipo`（代码、交易所、发行区间、进度），不写 `ticker`。

## 验证点到期时

1. 在 `changes.json` 里记一条新变动，说明结果，`from` 写当初的预期或指引，`to` 写实际。
2. 把这个验证点从 `calendar.json` 里删掉，或者改成下一个日期。
